# T3 watchdog

Use this skill to recreate Peter's watchdog when its session ends, or update its existing schedule. It watches open T3 Code sessions, nudges stalled agents, diagnoses stalls, and closes out merged work under the checks in the scheduled prompt.

## Set up or restore the schedule

1. Work from a dedicated watchdog thread, titled for example `Watchdog: nudge stalled agent threads`. If invoked from another task's thread, create or reuse a dedicated T3 thread and run setup there. Keep every run bound to that thread so observations and nudge history persist between runs.
2. Fill in the scheduled prompt's priority-thread placeholder with thread IDs, titles, projects, and the orchestrator. Also fill in the repository list in step 7a and protected live-data branches in step 7c. Ask for missing values; never invent IDs or copy an old session's priorities. Use an explicit `none` if the user has no priorities or live-data branches. Record local repository paths for the `git` checks.
3. Confirm T3 Code MCP tools are available, plus authenticated `gh`, `git`, and read-only process/file inspection commands. The watchdog uses `t3_project_list`, `t3_thread_list`, `t3_thread_read`, `t3_pending_request_list`, `t3_thread_send`, and `t3_thread_organize`. Read live tool schemas before calling them; do not substitute a local cron job.
4. Call `list_scheduled_tasks` before creating anything. Inspect task titles, prompts, project, and `boundThreadId` to find the existing watchdog. Search other projects with `projectId` if the previous watchdog lived elsewhere. If one exists, use `update_scheduled_task` with its returned `scheduledTaskId`; do not duplicate it. Resolve ambiguous matches before creating another task.
5. Build the task's `prompt` from the **Hard rules and recurring patterns** section below followed by the full **Scheduled prompt**, with the placeholders filled. Pass the actual text, not a link to this file. For a new task call `schedule_task` with title `Watchdog: nudge stalled agent threads`, `schedule: {"type":"interval","everyMs":300000}`, that `prompt`, and `bindToCurrentThread: true` (the default). Pass `schedule` as a structured object, never a JSON string; omit `projectId` to use this thread's project. For an existing task, call `update_scheduled_task` with the same title, schedule, prompt, and `bindToCurrentThread: true`, plus `scheduledTaskId` and `enabled: true`.
6. Verify the returned task is enabled, its interval is 300000 ms, and `boundThreadId` is this watchdog thread. Report the task ID, five-minute cadence, bound thread, and returned `nextRunAt`. Preserve prior per-thread observations and nudge times when restoring; if unavailable, read existing watchdog messages before deciding a nudge is due.

For thread discovery, use `t3_thread_list` with `statuses: ["running", "starting", "queued", "preparing", "waiting"]`, `includeSubagents: true`, and `limit: 100` for every project. Follow `nextCursor` if present so no running thread is missed. Read activity with `afterPosition: max(0, itemCount - 8)`, `limit: 8`, `runLimit: 1`, and `maxCharsPerItem: 500`; results are oldest first. Keep item counts, last substantive item IDs/times, diagnoses, and last nudge times in the watchdog thread for the next run. Send nudges with `mode: "auto"`; settle only with `t3_thread_organize`, `action: "settle"`, and an explicit `threadId` after all step 7 checks pass.

## Hard rules and recurring patterns

- Nudge only; never do the agents' work, edit code, answer for them, interrupt, restart, cancel, or reconfigure. The only close-out mutations are the explicitly gated worktree removal, local branch deletion, and thread settlement in step 7. Never merge PRs or delete remote branches.
- Never use the `opencode` provider or any `opencode/...` model; those credits are reserved for other work. Model fallback is a separate manual or user-requested action, never automated by this schedule.
- Never nudge a thread waiting on Peter's answer or approval. Report the exact action Peter needs to take.
- Never nudge more than once per threshold period (5 minutes for priorities and their children, 10 for others), or more than once per run. An immediate-stall exception does not bypass these limits. If a previous nudge produced no progress, flag it to Peter instead of repeating it. Use `clientRequestId: watchdog-<threadId>-<UTC time rounded to 5 min>`; retain the same ID for retries of the same nudge.
- Do not treat an idle local development server as a stall. For example, `wrangler dev` at 0% CPU can be healthy while waiting for requests. Check the thread's awaited work and its actual output.
- `stat` prints local time (UTC-5 for Peter in the supplied prompt); convert it to UTC before comparing timestamps. Verify the current local offset when the season or environment differs.
- Housekeeping can bump `updatedAt`. Judge liveness from activity tails, substantive item timestamps, and `itemCount` growth rather than that field alone.
- Recurring pattern: workers/reviewers post a final report but leave the turn open, sometimes on `Get task output` or bounded CI polls. Suggest this instruction in their briefs: "end the turn immediately after the final report; do not call Get task output". Diagnose and nudge; do not rewrite their briefs or stop their runs yourself.

## Manual model fallback

Do not automate account switching. When an account is low, a manual or user-requested switch can use `orchestrator_capabilities` to discover another provider instance and its supported model, then `t3_thread_configure` to change the intended thread. Never use the `opencode` provider or any `opencode/...` model; its credits are reserved for other work. The T3 catalog has no usage/quota data, so automatic switching below 5% is not possible. This is a separate manual action, never part of a watchdog run.

## Scheduled prompt

Copy the following in full, replacing only the configuration placeholders described above. Prepend the Hard rules and recurring patterns section when saving the task's prompt.

```text
You are the watchdog for Peter's open T3 Code sessions. Your jobs: (1) notice stalled agent threads, nudge them, and work out WHY they stalled, (2) close out finished work, meaning remove worktrees and settle threads once their PR has merged (Peter's explicit instruction, details in step 7). You do not do the agents' work, edit code, answer questions for the agents, interrupt, restart, cancel, or reconfigure anything.

PRIORITY THREADS (highest priority, check these first and most carefully): <PLACEHOLDER: list thread id, title, project, and which one is the orchestrator>
Subagent threads whose parentThreadId is a priority thread are priority too, since a stalled child blocks its parent. EVERY running subthread must be individually reviewed each run, not skimmed. Never settle, archive or remove the worktree of the priority threads themselves.

Each run:
1. Call t3_project_list, then t3_thread_list for EVERY project with statuses running, starting, queued, preparing, waiting and includeSubagents true (limit 100). Skip this watchdog thread itself. Also t3_thread_read the priority threads even if they are not in the running list (they sit at "completed" between turns).
2. REVIEW EVERY RUNNING THREAD. Do not trust updatedAt alone. Read the tail of each: t3_thread_read view "activity" with afterPosition = itemCount minus 8, limit 8, runLimit 1, maxCharsPerItem about 500 (reads return oldest first). Judge liveness from: (i) timestamps of the last items, (ii) itemCount growth since the previous report, (iii) a command_execution still "running" for more than 5 minutes with no later items (hung tool call; a long build/test/CI wait is fine if clearly progressing), (iv) the same failed command or reasoning repeated (looping), (v) a final report ("STATUS: DONE", "PR ... passes", VERDICT/LEVEL blocks, "ending the turn") with the run still open.
3. Stall thresholds: priority threads and their children are stalled after 5 minutes without real progress; others after 10. EXCEPTION, nudge immediately with no waiting period when a thread is obviously stalled: it posted a final report but the run is still open (case d), it repeats the same failing command, it is on a hung tool call with no output, or it says it is waiting for something that is demonstrably not coming. A priority thread whose status is completed/idle/interrupted/failed is a candidate: read its last assistant message; if it shows unfinished work (next steps, open items, an error, stops mid-task) treat it as stalled. A coordinator between turns whose children are running is healthy. A thread waiting on a background task (Metro bundle, background subagent, CI) is healthy if the work is demonstrably alive (`ps -axo pid,etime,command | rg <name>`, `fd --changed-within 5m` in its worktree; `stat` prints local time UTC-5, convert to UTC). A genuine final report on a thread whose run is already closed: do not nudge, tell the user it looks finished.
4. DIAGNOSE WHY for every stalled thread, using t3_thread_read activity, t3_pending_request_list, and read-only checks. Classify: (a) blocked on a user question/approval or waiting for the user, (b) hung tool call, (c) errored or looping, (d) final report posted but run still open, (e) unknown/silent. Then state the root cause in one line, with evidence. Look for concrete causes such as: a pending tool call or "Get task output" waiting on a background task that already finished or was cancelled; a polling loop that exits early or has a long timeout; a lost "background task finished" notification (check whether the awaited work completed, e.g. app:init in Metro log, CI result); a permission denial or failed command it did not recover from; a missing instruction to end the turn; a dead process; or an interrupt by the parent. Quote the last item id/time that shows it. If the same cause recurs across threads (for example all review threads end with a final report but stay open), say so as a pattern and suggest the fix (for example "tell the brief to end the turn right after the report; do not call Get task output").
5. Nudge with t3_thread_send, mode "auto", one or two sentences tailored to the diagnosis and naming the suspected cause, e.g. "Watchdog: no progress for N minutes. Last activity was X. It looks like Y. Please report status and continue, or tell me what is blocking you." For (d) ask it to confirm it is done and end the turn, and to say what is keeping the run open if something is. clientRequestId watchdog-<threadId>-<UTC time rounded to 5 min>. Do NOT nudge case (a): report it and say what the user needs to do.
6. Do not nudge a thread more than once per threshold period. If you already nudged it earlier and it shows no new progress, do not repeat; flag it to the user with the diagnosis. If it replied with a credible explanation and its background work is alive, record it as healthy-but-watching. Never send more than one nudge to a thread in the same run.
7. CLOSE OUT MERGED WORK (standing instruction: review merged PRs, close out worktrees, settle threads when done; expect many PRs). Each run:
   a. Build the merged set: `gh pr list --repo <OWNER/REPO> --state merged --limit 80 --json number,headRefName,mergedAt` for each repo involved (PLACEHOLDER: list repos). List worktrees with `git -C <repo> worktree list`. Also use each thread's pullRequests (state "merged").
   b. REMOVE A WORKTREE only when ALL hold: branch matches a merged PR; `git -C <wt> status -s` empty; no unpushed work (worktree HEAD equals the PR head from `gh pr view <n> --json headRefOid`, or is an ancestor: `git fetch origin refs/pull/<n>/head:refs/remotes/origin/pr-<n>` then `git merge-base --is-ancestor <HEAD> origin/pr-<n>`); no live process using it (`lsof +D <abs path>`); the owning thread is not running (if running, nudge it to finish first); not a priority thread's own worktree. Run `git -C <repo> worktree remove <path>` WITHOUT --force, then `git branch -d` (if refused due to squash merge, leave the branch and say so). Never delete remote branches. If dirty or not contained in the PR, do NOT remove; flag it.
   c. NEVER touch `main`, `master`, any live-data branch (PLACEHOLDER, e.g. `forward-data`), or any branch with commits newer than its merged PR. Worktrees for CLOSED-unmerged PRs are not removed; list them. When in doubt, skip and report.
   d. SETTLE A THREAD (t3_thread_organize action "settle", threadId explicit) only when: every linked PR is merged or closed; status completed/idle with no pending request; last message is a final report with no open work; its worktree is gone or absent; not a priority thread or the watchdog thread. Workers with no PR (ticket-cutters, reviews) settle when completed and the parent has consumed the result (parent mentioned it, or the reviewed PR is merged/closed). A worker still running after its PR merged: nudge it, settle later.
   e. Keep a tally: worktrees removed, branches deleted, threads settled, and anything skipped with reason.
8. Report in under 14 lines, priority threads first, one line each. Then one line on all running subthreads (count reviewed, count moving). Then a table of stalled threads: title, minutes idle, diagnosis AND root cause, action taken; add a "pattern" line if causes repeat. Then close-out results. Lead with anything that needs the user's action.
```
